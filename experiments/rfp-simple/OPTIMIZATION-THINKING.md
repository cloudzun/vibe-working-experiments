# 🔍 优化思路详解

## 问题诊断 → 解决方案

### 问题 1：路径混乱

**根本原因**：
```
❌ 项目顶层有 skills/
❌ 实验目录有 materials/
❌ 脚本用相对路径找 materials
❌ 从不同目录运行脚本 → 找不到 materials
```

**优化思路**：
```
✅ 整体移动：把 skills/ 移到 experiments/rfp-simple/
   为什么？实验专属的 Skill，应该在实验目录

✅ 新建 scripts/ 目录：集中管理所有脚本
   为什么？脚本与素材在同一目录，易于定位

✅ 添加智能检测：而不是死板的相对路径
   def find_materials_dir():
       candidates = [
           实验目录/materials,     # 首选
           当前目录/materials,     # 备选
           脚本目录/materials,     # 备选
       ]
   为什么？支持多种运行方式，用户友好
```

**验证方式**：
- 从项目根目录运行 → ✅ 脚本能找到 materials
- 从实验目录运行 → ✅ 脚本能找到 materials
- 错误提示清晰 → ❌ 用户知道怎么做

### 问题 2：Skill 不会自动调用

**根本原因**：
```
❌ Skill 只是 YAML 配置文件
❌ 没有告诉 AI 何时调用
❌ 没有定义触发条件
❌ 需要用户手动指定运行
```

**优化思路**：

#### Step 1: 定义 Skill 的"角色"
```yaml
# ✅ 每个 Skill 有明确的职责
rfp-analyzer:
  description: "分析 RFP 文档，提取需求"
  role: "投标分析专家"

knowledge-searcher:
  description: "在产品文档中检索答案"
  role: "知识管理专家"

response-generator:
  description: "生成投标响应文档"
  role: "投标文档顾问"
```

#### Step 2: 定义触发条件（何时调用）
```yaml
# ✅ AI 知道什么时候应该用哪个 Skill
rfp-analyzer:
  triggers:
    keywords:
      - "分析 RFP"
      - "找出需求"
      - "提取需求"
    file_patterns:
      - "*.docx"
      - "RFP*"
    contexts:
      - "用户提到 RFP 文件"

knowledge-searcher:
  triggers:
    keywords:
      - "找答案"
      - "检索答案"
      - "在产品文档中"
    contexts:
      - "需求列表已生成后"
      - "用户要求检索答案"
```

#### Step 3: 工作流自动流转
```
用户："分析 @RFP.docx"
  ↓ AI 识别关键词"分析"+"RFP"
  ↓ 自动调用 rfp-analyzer
  ↓ 输出：21 个需求

用户："找答案"
  ↓ AI 识别关键词"找答案"
  ↓ 知道之前已生成需求列表
  ↓ 自动调用 knowledge-searcher
  ↓ 输出：需求-答案对照表

用户："生成文档"
  ↓ AI 识别关键词"生成"
  ↓ 知道之前有需求和答案
  ↓ 自动调用 response-generator
  ↓ 输出：Word 文档
```

**为什么不需要 /skill load？**
```yaml
# ✅ 更好的方式：在 Skill 中定义触发条件
# ❌ 不好的方式：每次都手动加载

# Skill 的触发条件相当于大脑的反射弧：
# 看到关键词 → 自动反应 → 调用相应 Skill
```

### 问题 3：Skill 容易编造数据

**根本原因**：
```
❌ AI 很聪明，但容易"幻觉"编造信息
❌ 没有明确的约束
❌ 没有说明什么能做，什么不能做
```

**优化思路**：

#### Step 1: 明确的纪律要求
```yaml
discipline:
  - ✅ 只能从提供的材料中检索答案
  - ❌ 不得编造数据或功能
  - ❌ 不得引用外部知识
  - ⚠️ 找不到答案时明确标注"材料中未找到"
  - ✅ 所有答案必须标注来源
```

#### Step 2: 机制保障（不只是说说）

**对于 knowledge-searcher**：
```
❌ 如果找不到答案，不编造
✅ 而是标注 "⚠️ 材料中未找到"

❌ 如果多个来源冲突，不选择
✅ 而是列出所有版本让用户选择
```

**对于 response-generator**：
```
❌ 如果需求没有答案，不编造
✅ 而是使用占位符 [补充内容]

❌ 如果需要补充信息，不凭空编造
✅ 而是提示用户"需要人工补充"
```

#### Step 3: 验收标准
```
✅ 验证是否遵守纪律：
  1. 所有答案都有来源
  2. 没有编造的信息
  3. 未找到答案时明确标注
  4. 占位符机制正常工作
```

## 💡 设计原则总结

### 原则 1: 职责单一
```
❌ 一个 Skill 做所有事
✅ 每个 Skill 做一件事

rfp-analyzer → 只分析 RFP，提取需求
knowledge-searcher → 只检索产品文档
response-generator → 只生成投标文档
```

### 原则 2: 触发条件明确
```
❌ "可能什么时候需要"
✅ "当用户说这些关键词时"

定义清晰的触发条件 → AI 知道何时调用
```

### 原则 3: 约束机制有效
```
❌ "请不要编造"（说说而已）
✅ 设计机制保证不会编造

使用占位符 [补充内容] → 必须人工填充
标注来源 → 可验证、可追溯
```

### 原则 4: 用户友好
```
❌ 复杂的错误信息
✅ 清晰的错误提示，说明解决方案

找不到 materials 目录 → 提示用户：
  "请在实验目录运行：cd experiments/rfp-simple"
```

## 📊 优化效果对比

| 方面 | 优化前 | 优化后 |
|------|--------|--------|
| **用户体验** | 需手动指定运行、指定脚本 | 自然语言交互，自动调用 |
| **可靠性** | 容易出错（路径问题） | 智能检测，友好提示 |
| **数据安全** | AI 可能编造 | 机制保证准确性 |
| **可维护性** | 脚本散落，难以维护 | 清晰的职责划分 |
| **可扩展性** | 添加新实验困难 | 轻松添加新实验 |

## 🎯 关键洞察

### 洞察 1: 结构即文档
```
好的目录结构本身就是文档：
- materials/ → 素材在这
- skills/ → Skill 定义在这
- scripts/ → 脚本在这
- outputs/ → 输出在这

用户一眼就能理解
```

### 洞察 2: 触发条件 = 人类认知
```
人类：看到"分析 RFP"→ 想到要用分析 Skill
AI：看到"分析 RFP"→ 自动调用 rfp-analyzer Skill

触发条件就是让 AI 的思维方式接近人类
```

### 洞察 3: 约束机制 > 道德告诫
```
❌ "请不要编造" → 无法保证
✅ 使用 [补充内容] 占位符 → 必须人工填充

机制 > 文字承诺
```
